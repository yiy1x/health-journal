# 本地优先个人医疗助理：现状调研与产品建议

调研日期：2026-11-13（Asia/Shanghai）。

## 0. 结论先行

你想做的不是一个只回答医学问题的聊天机器人，而是一个**由个人持有数据、贯穿多年就医经历的健康档案与行动助理**：本地保存原始资料，像诊所一样组织各科就诊、检查、诊断和用药，同时记录症状、安排日常饮食，并帮助准备就医问题。

**可行，而且值得做；但应该把“可靠保存事实”和“生成医学推测”严格分开。**

本次核查的生态已经走到以下阶段：

- 个人病历保存、就诊时间线、症状和用药记录：已有持续维护、可部署的开源实现。
- PDF/图片抽取、指标标准化、跨年趋势和带来源的 AI 问答：已有完整应用和可复用组件，但不能假定中文病历准确率、离线能力和隐私边界都已验证。
- 每日食谱、购物清单、营养记录：独立项目较成熟，但不是自动结合多种疾病与用药约束的临床营养系统。
- 对“可能是什么病”的辅助解释：技术上可以生成候选原因，但面向普通人的可靠性不能由医学考试分数、项目星标或演示来证明。
- 将以上能力整合成**中文优先、真正离线、跨科关联、证据可追溯、安全饮食建议**的一体化个人产品：在本次核查范围内，没有发现已经充分验证、可以不加评估直接满足全部需求的项目。

**建议的方向：中文个人健康档案 + 原件可追溯的 AI 助理 + 受规则约束的饮食规划；不是“自动确诊的私人医生”。**

## 1. 调研方法与证据边界

### 1.1 本次实际做了什么

1. 检索个人健康档案、自托管医疗 AI、医疗 AI 真实用户研究、国内食养指南和医疗软件监管资料。
2. 通过 GitHub 官方 API 核查 14 个相关仓库的描述、创建时间、归档状态、星标和许可证识别结果。
3. 阅读这些仓库的 README；对 7 个重点候选额外核对最新正式发布与默认分支最近提交。
4. 对 4 个重点候选检查代码目录；抽样阅读人工确认工具代码、检验结果 schema、安全文档和云端抽取架构决策。
5. 直接阅读 Nature Medicine 研究、Google MedGemma 模型卡、国家卫健委食养指南通知、USDA 食物数据文档和国家药监局公告。

**没有安装或运行这些项目，没有上传任何个人病历，没有进行临床验证，也没有做完整代码安全审计。**

### 1.2 如何理解文中的判断

- **已核验事实**：仓库是否归档、许可证文本、发布记录、代码中存在的特定逻辑、官方文档明确写出的限制。
- **项目自述**：README 宣称的功能、性能、隐私和测试数量；不等于独立验证。
- **调研判断**：对个人使用适配度、开发成本、集成顺序的分析。
- **建议设计**：本文为新项目提出的架构与验收要求，不代表现有项目已经实现。

星标只反映关注度，不代表医学有效性或安全性。`pushed_at` 可能来自非默认分支，因此重点表格使用默认分支提交日期；日期按北京时间列示。GitHub 把一个 release 标成非预发布，也不等于临床可用。

## 2. 把需求拆成六个模块

| 模块 | 你实际需要的能力 | 不应混淆的边界 |
|---|---|---|
| 本地资料库 | 病历、化验、处方、影像报告、照片、原文件与备份 | 本地存储不代表 OCR、模型和同步也在本地 |
| 个人诊疗档案 | 按科室、医院、就诊事件、健康问题组织历史 | 借鉴诊所档案，不必引入医院收费与挂号系统 |
| 长期指标 | 同指标跨医院比较、保留原单位和参考范围 | 检验异常不自动等于疾病；跨实验室未必直接可比 |
| 症状与病程 | 开始时间、频率、严重程度、诱因、伴随症状、变化 | 自述、医生诊断、AI 假设必须分开 |
| 饮食规划 | 每日三餐、份量、替代食物、营养估算、购物清单 | 菜单生成不同于多病共存患者的医学营养治疗 |
| AI 助理 | 历史问答、报告解释、缺失信息追问、就医摘要 | 不自主确诊、开药、改剂量或排除急症 |

一个典型使用链路应当是：

> 导入某次就诊报告 → 抽取并核对 → 关联到科室与健康问题 → 更新趋势 → 记录当前症状 → 生成带原件引用的解释和就医问题 → 在已经确认的饮食约束下生成菜单。

### 3.2 Mirobody：优先验证 AI 与标准化能力

**官方自述的能力**：

- 汇入化验报告、照片、穿戴数据、健康日记和基因文件。
- 用术语与单位标准化把不同报告放到统一历史中；每项读数能回溯来源。
- 内置 MCP 接口，供其他客户端访问健康数据工具。
- 支持本地 Docker + llama.cpp，或本地应用 + 云模型。
- 支持中文术语解析；README 展示血红蛋白等中日文名称解析到同一编码。
- 完整本地配置声明需约 16 GB 内存，其中至少 8 GB 给 Docker；CPU 回答可能需要数分钟。这是项目要求，不是本次实测。

**为什么适合借鉴**：它不是简单地把所有 PDF 塞进向量库，而是把“采集、标准化、基于数据库工具回答”分开。长期医疗数据最重要的资产是可核对的结构化事实。

**必须注意的实际限制**：

- 当前安全文档明确说默认配置面向本地单用户评估，不应原样暴露到网络。
- 文档说明数据库内容加密覆盖部分文本与文件字段，并不覆盖所有观察值和基因数据；不能称为“全库已加密”。
- 云模型配置会发送相关文档、问题和检索数据；MCP 接入云端客户端也不会天然保持隐私。
- 默认分支安全说明还列有旧版本密钥迁移和设备连接风险，试用必须固定版本、清理演示账号并核对安全配置。
- 不提供诊断和处方。没有证据证明其已有符合你需求的医学饮食闭环。

**判断**：优先用合成报告做技术验证；更适合复用标准化引擎和可追溯问答思路，不应因为功能完整就直接存入唯一一份真实病历。

来源：[README](https://github.com/thetahealth/mirobody)、[固定提交安全说明](https://github.com/thetahealth/mirobody/blob/a2b5471912c548c9645a0c7af555a017e4001f4e/SECURITY.md)。

### 3.3 Health Assistant：完整产品形态接近，但仍是 Beta

**官方自述的能力**：

- 把就诊、病历、化验指标、药物、过敏、疫苗、穿戴设备数据放在一起。
- 长期健康问题以 health journeys 组织，而不仅是按文件夹存储。
- OCR + AI 抽取、指标标准化、趋势、来源引用、随访提醒。
- FHIR 增强型关系数据模型和 FHIR API。
- AI 提出修改建议，由人查看卡片后确认。
- 可配置本地 Ollama/vLLM 或其他兼容接口。

**本次代码抽查确认**：`propose_create_clinical_event` 的实现先查类型、构造 `PROPOSED` 状态的人工审核任务，而不是在该工具中直接创建健康事件。这证明人工确认并非只写在宣传语里；但没有据此推断整个系统所有写入路径均已安全审计。

**限制**：

- 明确为 Beta、没有医疗用途认证。
- 当前栈为 React + FastAPI + PostgreSQL/TimescaleDB + Redis/Celery，对单人桌面软件偏重。
- 文档说仅英语、希腊语；中文体验和中文病历解析需要另做验证。
- 原生手机应用仍在计划中；PWA 不等于完整离线桌面数据库。
- README 顶部是 v0.9.0，但部分限制章节仍写 0.8.x，存在文档滞后。
- 项目宣称有大量单元测试，但同时说明尚无端到端测试套件；本次没有执行测试。

**判断**：特别值得借鉴其“AI 提议、用户确认”的权限模型和病程组织；若目标是轻量桌面产品，不宜直接把整套基础设施搬进来。

来源：[仓库](https://github.com/health-assistant-io/health-assistant)、[抽查的人工确认工具](https://github.com/health-assistant-io/health-assistant/blob/75fa4c91962026643cdaa646c640e07957a81503/backend/app/ai/tools/hitl_proposals.py)。

### 3.4 MediKeep：更务实的个人档案底座

MediKeep 原名 Personal Medical Records Keeper，使用 React + FastAPI + PostgreSQL。

文档、仓库目录与 schema 显示它覆盖用药、疾病、就诊、症状、检验、附件和报告等传统档案能力；有症状日历、时间线、用药提醒相关实现。抽查的检验 schema 包含数值、单位、日期等结构化字段，不只是附件管理。

**优点**：关注点贴近“我看过哪些科、查出过什么、吃过哪些药、如何给下一位医生展示病史”。Apache-2.0 也较适合后续二次开发。

**缺口**：本次没有看到足以直接交付你所需“疾病相关膳食推荐 + 安全症状推理”的证据。OCR 自动化、中文适配和 AI 层仍需评估或开发。

**判断**：如果想先得到一个能长期使用的病历本，而不是先做炫目的 AI 演示，它是优先试用对象。

来源：[仓库](https://github.com/afairgiant/MediKeep)、[LICENSE](https://github.com/afairgiant/MediKeep/blob/main/LICENSE)、[抽查的检验 schema](https://github.com/afairgiant/MediKeep/blob/719ca358ac9e0c1ce145183f1820c79d9d783430/app/schemas/lab_result.py)。

### 3.5 MedMe：中文方向很接近，但“全部本地”不能照搬旧描述

**README 描述的亮点**：中文优先、手机采集、OCR、原件永久保留、健康时间线、DICOM 查看、加密分享。Rust 内核结合 Flutter 手机端及 Tauri 桌面端，事件日志与内容寻址文件为事实源，SQLite 为可重建的派生缓存。桌面端在 README 中仍写明没有公开安装包。

**本次最值得注意的差异**：

2026-09-14 的已接受架构决策 `ADR 0010` 明确替代此前“识别全链路都在端上”的原则：OCR 仍在本地，但后续结构化抽取经本地脱敏后送到项目代理，再调用 DeepSeek。该文档说明需账号会话，云端整理开关默认开启，并承认脱敏无法保证不遗漏。

这份较新的决策文档与 README 的“零服务器、本地优先”简化描述之间存在重要差别。它也区分了存储加密和识别时的云传输。

**判断**：是很有价值的中文产品和数据保留设计参考，但不能直接作为“严格离线、病历永不出设备”的现成推荐。还必须核对目标发行版是否包含新路径、登录后的默认配置，以及当前代码的真实行为。

来源：[README](https://github.com/Chesterguan/medme)、[固定提交 ADR 0010](https://github.com/Chesterguan/medme/blob/9c9251d7abb80472b2bfcef51ea8552ae1628e90/docs/ADR/0010-cloud-llm-extraction-and-accounts.md)。ADR 中的抽取指标为项目自测，本报告不将其当作独立临床准确率。

### 3.6 Mere Medical、YourPHR、Fasten：个人档案生态的演进

**Mere Medical**：长期维护的离线优先个人病历聚合应用，支持多个患者门户，强调时间线和数据汇总。MIT 许可。其患者门户连接偏向美国医疗系统，不能推断能直接连接国内各医院；README 说明主要由一位同时是住院医师的开发者维护。

**Fasten OnPrem**：曾是这一领域的重要项目，但本次官方 API 返回 `archived: true`。更关键的是当前 README 明确说开源版**不能直接从医疗机构导入**，只能手工输入或导入其他途径获得的 FHIR Bundle。不能把商业 Fasten Connect 的机构连接能力归到开源版头上。

**YourPHR**：自述为 Fasten OnPrem 的独立社区延续。支持自托管、FHIR R4 导入和手工输入，但 README 中聊天问答、部分家庭和穿戴能力仍标为 Future。新项目、社区规模小，需要评估长期维护与迁移成本。

**判断**：如果已有标准化 FHIR 资料，它们值得研究；如果主要是国内医院照片、PDF、微信截图，优先级低于中文导入和人工校对链路。

来源：[Mere](https://github.com/cfu288/mere-medical)、[Fasten](https://github.com/fastenhealth/fasten-onprem)、[YourPHR](https://github.com/jwilleke/yourphr)。

### 3.7 OpenHealth：容易理解的本地 AI 原型，不宜只凭热度选型

OpenHealth 支持输入体检、血检、身体信息、家族史和症状，通过解析后数据进行 AI 对话；README 明确说明 Docling 与 Ollama 可组成全本地链路。

但本次核对的默认分支最近提交为 2026-01-06，最新正式发布为 2025-02-21 的 v0.2.0。与部分小而持续迭代的项目相比，其高星标并不意味着维护更活跃。图示中出现穿戴平台，也不能直接作为每个集成都已交付的证据。

**判断**：可以学习交互与本地解析的原型设计；不作为未经验证的长期核心依赖。

来源：[OpenHealth](https://github.com/OpenHealthForAll/open-health)。

## 5. “每日吃什么”已经能做到哪一步

### 5.1 可以比较可靠地工程化的部分

- 保存自己的家常菜库、口味、预算、烹饪时间和可用食材。
- 根据份量计算能量和营养素，生成三餐与购物清单。
- 排除已经确认的过敏原和不接受的食材。
- 在医生或营养师确认的饮食目标下选菜、换菜并解释原因。
- 保存计划版本和实际饮食，观察执行情况。

### 5.2 尚不能交给模型自由发挥的部分

- 同时存在多种疾病、特殊生理阶段、药物或治疗要求时如何处理冲突。
- 把一个检验数值异常直接转换成长期限制性饮食。
- 不知道份量、烹饪方式和油盐用量时，给出看似精确的营养数字。
- 把菜谱网站或模型生成的营养数据视作可靠成分分析。
- 用“可能患病”的 AI 假设覆盖医生已有的饮食医嘱。

**建议分工：数据库提供营养事实，规则引擎检查约束，模型负责可读表达和有限范围内的搭配。**

### 5.3 可以使用的数据与指南

**USDA FoodData Central**：官方提供 CSV/JSON 下载，适合导入本地数据库。调研当天下载页已有 2026-10 的 Foundation Foods 与 Branded 数据。不同数据类型分别来自分析、调查或标签，不应把全部条目当作同等级证据；国外数据库也不能直接保证中式成菜覆盖。[数据说明](https://fdc.nal.usda.gov/data-documentation)、[下载页](https://fdc.nal.usda.gov/download-datasets)。

**Open Food Facts**：wger 已使用它做食品记录，是包装食品的候选数据源；本次没有独立审核其完整数据许可与质量，所以正式接入前应单独核查，不能与代码许可证混为一谈。

**国家卫健委食养指南**：2024 年通知包含成人高尿酸血症与痛风、成人肥胖、儿童青少年肥胖、成人慢性肾脏病四项指南，可作为中文规则整理和营养专家复核的来源起点。这里核对了发布通知与附件存在，不代表已经逐条审读并编码了指南。[官方通知](https://www.nhc.gov.cn/sps/c100088/202402/9ba512ba8e314a47a181db11d2fa188d.shtml)。

**中国食物成分与菜谱数据**：需要确认授权、版本、可食部、生熟状态、成菜份量和油盐；本次没有确认一个可无条件随 GitHub 仓库再分发的完整中式食物成分库。建议从经审核的小型家常菜数据集开始，而非抓取大量不明许可菜谱。

## 6. “可能得什么病”到了哪一步

必须区分三个不同任务：

| 任务 | 可接受输出 | 不可直接宣称 |
|---|---|---|
| 当前症状解释 | 常见可能原因、需要补充的信息、需医生评估的问题 | 确诊或“肯定没有严重问题” |
| 未来患病风险 | 在适用人群和输入完整的前提下，使用经验证的特定风险工具 | 用通用模型随意生成百分比 |
| 病情追踪 | 关联既往已确认诊断、当前症状和复诊变化 | 自动把历史怀疑升级为已确诊 |

### 6.1 最新可核实的研究警示

2026-02-09 发表的 Nature Medicine 随机预注册研究纳入 1,298 名参与者，设置 10 个医疗情景：

- 模型单独处理完整情景时，识别相关疾病平均为 94.9%。
- 参与者实际使用相同模型时，识别相关疾病低于 34.5%，判断下一步处置低于 44.2%，均未优于对照组。
- 作者把信息传递和人机交互列为重要失败点，强调真实用户测试不能被医学知识基准或模拟患者代替。

**不能过度解读**：该研究使用 GPT-4o、Llama 3、Command R+，数据采集于 2024 年，且是情景任务，不是所有 2026 年模型、真实临床病例或本项目的统一准确率。它证明的是评估方法的缺口，不是证明所有医疗 AI 都无用。

来源：[研究全文](https://www.nature.com/articles/s41591-025-04074-y)。

### 6.2 本地医疗模型也不是“装好就是医生”

Google 的 MedGemma 1.5 4B 模型卡列出医疗文档抽取、EHR 理解、医学图像等能力，说明本地医疗 AI 组件已不局限于聊天演示。

但官方同时明确：模型需要针对具体场景适配与验证；输出不应直接用于临床诊断、患者管理或治疗建议，须独立核验。模型卡还说明多轮应用未经过相应评估或优化，且安全评估主要使用英文提示。

因此不应把“医学专用”“参数量小”或“开源权重”当作中文个人医疗助理的默认最优解。适合先比较它在中文报告抽取任务上的表现，而不是先让它承担诊断职责。

来源：[官方模型卡](https://developers.google.com/health-ai-developer-foundations/medgemma/model-card)。

### 6.3 你的项目中更安全的落点

- 首先把用户描述整理成可供医生理解的症状记录。
- 缺失关键上下文就追问或明确无法判断，不用旧记录自动填补当前事实。
- 涉及危险症状时优先给及时就医提示，不能让模型以“看起来正常”覆盖安全提示。
- 列举可能原因时给出支持证据、反对证据和信息缺口，不给无依据概率。
- AI 候选进入独立的“讨论/假设”区域，不进入已确诊疾病清单。
- 用户点击“保存 AI 建议”不等于医生确诊；确诊状态需要相应临床来源。
- 不自主生成处方或调整剂量，不把软件当作急诊判断的唯一依据。

## 7. 本地数据库应怎样设计

以下是建议设计，不是对某个仓库既有实现的描述。

### 7.1 三种“本地”必须分清

| 模式 | 本地保存 | 模型处理 | 对隐私的含义 |
|---|---|---|---|
| 严格本地 | 是 | 本机模型、OCR、嵌入与检索 | 初始化下载后可离线；仍需备份和设备安全 |
| 本地优先 + 可选云模型 | 是 | 按请求发送部分数据给云厂商 | 并非数据不出设备；需可见范围与明确授权 |
| 自托管到云服务器 | 在自管服务器 | 本地或远程模型 | 不等于保存在自己的电脑上 |

还应审计错误上报、分析埋点、字体/CDN、远程图像、网页搜索、备份、通知、MCP 客户端等旁路。只关掉聊天 API 不代表全应用离线。

### 7.2 推荐的起步架构

**单人单机第一版**：本地 Web 应用或桌面外壳 + SQLite + 本地附件目录 + 确定性抽取校验 + 可替换模型适配层。

- SQLite 保存结构化档案、关系与版本。
- 原文件独立保存，按内容哈希去重并保持只读；修改提取结果不覆盖原件。
- 本地全文检索优先，必要时再增加向量检索；向量库不是唯一数据库。
- 本地 OCR 和模型按需启动，没开模型也能查看、编辑、导入导出档案。
- 如果之后要支持多用户、NAS、持续穿戴数据，再考虑 PostgreSQL；不应一开始就引入全套医院信息系统。
- 数据库加密可评估 SQLCipher 或操作系统级加密方案，但附件、备份和密钥需要同时设计，不能只保护数据库文件。

### 7.3 核心实体

| 实体 | 应保留的信息 |
|---|---|
| 人员档案 | 本人/家属隔离、年龄相关信息、过敏、家族史、来源 |
| 医院与科室 | 原名称、标准化名称、就诊关联 |
| 就诊事件 | 日期精度、主诉、医生、科室、已记录诊断、处置与附件 |
| 健康问题 | 同一问题跨科室跨年的事件集合、当前状态 |
| 检查报告 | 原件、机构、采样/报告时间、报告状态、来源定位 |
| 检验观察值 | 原名、标准名、数值/文本/比较符、原单位、标准单位、参考范围 |
| 用药记录 | 医嘱来源、剂量单位、频次、起止时间、实际服用与处方区分 |
| 症状事件 | 开始/结束、严重度、频率、诱因、伴随症状及明确否认项 |
| AI 假设与建议 | 输入资料版本、模型、来源、生成时间、局限、人工审核状态 |
| 饮食计划与实际记录 | 食谱、份量、生熟状态、营养来源、约束、执行情况 |
| 审计与备份 | 创建/修改者、版本、来源、导出范围、恢复校验 |

数据模型可参考 FHIR 的 Patient、Encounter、Condition、Observation、DiagnosticReport、MedicationStatement、AllergyIntolerance、DocumentReference、Provenance 等概念，为导出预留映射；第一版不必先部署完整 FHIR 服务器。本次 FHIR 官方页面访问超时，具体字段与规范性约束应在实施前重新查阅正式规范，不把这里的设计表当作完整 FHIR 定义。

### 7.4 五个最容易被低估的难点

1. **日期**：症状开始、就诊、采样、出报告、导入时间不是一回事；只知道年份时不要编造月日。
2. **单位**：单位换算必须绑定具体检验项目，不能仅看到 mg/dL 就统一换算；不同方法学可能不能合并趋势。
3. **状态**：未检查、未发现、明确阴性、疑似、已确诊、已排除不是同一个状态。
4. **原件定位**：保存页码、文本片段或框坐标，让每个关键数字可以点回原文；整份报告存在相同数字不等于该行被正确识别。
5. **跨科关系**：同一个健康问题可以同时关联多个科室；不要为每个科室复制一份彼此矛盾的独立病历。

## 8. GitHub 发布与隐私

**上传的是源代码和合成演示数据，不是个人医疗数据库。** 私有仓库也不应作为真实病历的默认备份方式。

建议公开的内容：代码、schema、空配置模板、安装指南、来源许可清单、安全说明、合成病例、无真实信息的截图、测试。

禁止默认纳入仓库：真实附件、数据库、数据库 WAL/SHM、OCR 缓存、向量索引、聊天记录、备份、运行日志、访问令牌和模型 API key。

数据目录应位于仓库外，例如操作系统的应用数据目录；用户还应知道文档目录是否被 iCloud/其他云盘自动同步。`.gitignore` 是防误操作的一层，不是完整安全控制，也不能清除已提交历史。

还需要：

- 推送前的敏感文件与凭证检查；CI、Issue、错误日志和截图也只能使用合成数据。
- GitHub Pages 如有演示，只放合成数据，不把真实病历打进静态资源。
- Codespaces 是 GitHub 云端环境，不能视为本地运行。
- 加密备份与恢复演练；数据库与附件需取得一致快照，不建议把正在写入的 SQLite 文件直接交给普通云盘双向同步。
- 第三方代码、模型权重、医学术语、营养数据的许可证分别审核。

监管方面，国家药监局已有 AI 医用软件分类界定指导文件。当前可验证的官方公告说明该监管框架存在；本报告不是法律意见，也不据此判断本产品的具体类别。若将来公开提供诊断、疾病预测或治疗建议，应针对真实功能、预期用途、用户对象和发布地区做专门合规评估，不能只靠“仅供参考”免责声明。

来源：[国家药监局公告](https://english.nmpa.gov.cn/2021-07/08/c_660267.htm)。

## 9. 三条实施路线

| 路线 | 做法 | 优势 | 代价 |
|---|---|---|---|
| A：先拼装验证 | MediKeep/Mirobody 二选一作为档案或 AI 试验底座，Mealie 管菜单 | 较快知道自己真正用哪些功能 | 多套 UI、跨系统关联、授权和同步复杂 |
| B：二次开发 | 深入评估 MediKeep 或 Health Assistant，围绕现有数据模型扩展 | 少做基础档案管理，Apache 许可较友好 | 继承服务器架构、上游升级与中文适配成本 |
| C：小而完整的新项目 | 自建轻量本地档案，借鉴人工审核与来源追踪，按许可复用标准化组件 | 最贴近单机、中文与统一体验，架构可控 | 导入、迁移、测试和安全需要自己负责 |

**建议顺序：先做有限范围的 A 类验证，再决定 B 或 C。** 不建议马上 fork 一个高星标项目后大规模改造，也不建议一开始就造复杂多 Agent 医院。

如果“本地单机、中文、一体化、方便 GitHub 分发”是最重要的目标，长期更倾向 C；如果“尽快能记病历”优先，B 可能更节省时间。

## 10. 推荐分阶段交付

### 阶段 1：可信档案，而不是智能诊断

- 单用户、本地资料库；就诊、科室、问题、用药、过敏与症状记录。
- PDF/图片导入、原件保存、人工录入与基础 OCR 待确认队列。
- 时间线、全文检索、导出和加密备份恢复。
- 合成数据演示和 GitHub 发布检查。

**完成标准**：不用任何 AI 也能作为长期个人病历本；更换模型不会损失事实。

### 阶段 2：有证据的 AI 助理

- 自动抽取只形成草稿，确认后写入正式结构化档案。
- 历史问答和趋势分析先查数据库，所有关键医学数字能回溯原件。
- 同一健康问题跨科关联；生成复诊摘要与医生提问清单。
- 显示所用数据日期、缺失项、模型模式和外发范围。

**完成标准**：不能捏造未记录的检验、日期、药物或诊断；AI 没有直接修改确诊记录的权限。

### 阶段 3：受约束的饮食与日常管理

- 小型且经审核的中式家常菜库，按份量与来源计算营养。
- 基于已确认的过敏、饮食目标和医嘱制定菜单；冲突就停止自动推荐并提示复核。
- 支持替换食材、购物清单、实际饮食、症状日志与复诊提醒。
- “可能原因”仅作带证据的信息整理，不做自主疾病预测器。

**完成标准**：推荐过程可解释；禁忌测试可复现；没有足够健康上下文时退回一般健康饮食信息，而非伪装成个体化治疗方案。

## 11. 下一步应该验证什么，而不是先写什么

使用一组自造或明确授权的样本，对三个优先候选做同口径测试：MediKeep（档案）、Mirobody（解析与问答）、Health Assistant（病程与人工确认）。

| 测试方向 | 关键失败例 |
|---|---|
| 报告抽取 | 小数点错、项目与值错配、参考范围错行、阴阳性翻转 |
| 临床语义 | “无发热”变“发热”、“排除某病”变“确诊某病” |
| 人员隔离 | 两名家庭成员的相似报告串档 |
| 数据生命周期 | 重复导入、报告修订、删除撤回、导出后恢复 |
| 长期问答 | 用旧数值回答“最近一次”、混淆采样日期与报告日期 |
| 权限 | 文档中的指令能否诱导 AI 发网请求、越权读取或写入 |
| 隐私 | 断网后哪些功能停止；联网时是否存在未授权外发 |
| 饮食 | 过敏食物被换个名字推荐、未计入调味料、未知营养值按零计算 |
| 安全提示 | 信息不足却给确定结论；风险提示被后续模型回答抵消 |

应分别统计字段级正确率、关键错误、来源可追溯率、拒答/追问情况、危险漏报，以及真实用户能否理解输出。不要把这些合并成一个漂亮但解释不清的“医学准确率”。

在正式承担分诊或疾病风险建议前，还需要临床专业人员参与的独立评估，普通软件单元测试不能替代它。

## 12. 最终建议

**值得做的核心不是“又一个会说医学术语的模型”，而是“可靠地记住我的健康事实，并能告诉我每条结论从哪来”。**

优先级建议：

1. 原件、本地档案、可恢复备份。
2. 多科就诊和长期健康问题的结构化关联。
3. 待确认抽取、可信检索、带原件引用的解释。
4. 受约束的饮食计划与实际记录。
5. 谨慎、可追溯的症状辅助解释。

这条路线既能保留你的“像个人诊所一样”的体验，也更适合安全地做成开源 GitHub 项目。当前阶段应先确定单机还是 NAS/手机协作、主要资料格式、严格离线是否必要；无需先决定用哪个“最强医疗模型”。
