# 手机优先与多端资料互传

适用版本：1.2.1，更新于 2026-11-14。手机端目前是**随身资料版**，不是桌面全部临床记录功能的移植，也不是已完成的自动同步系统。请先用合成资料体验、验证导出和恢复，再考虑保存真实资料。

## 三件事必须分清

| 方式 | 资料实际在哪里 | 当前状态 |
| --- | --- | --- |
| 电脑档案 | 运行 Python 的电脑 SQLite 与附件目录 | 已有完整桌面功能，仅允许本机访问 |
| 手机随身手记 | 手机当前浏览器、当前来源的 IndexedDB，加密快照 | 新增，拍照、相册、文件、文字、查看、关键词分类、备份 |
| 多端同步 | 两端交换各自保存的内容 | 本版仅手动原件互传/合并；未实现实时同步、账号或远程电脑访问 |

电脑浏览器打开 `/phone/` 时，手机版的资料也存在**这台电脑的浏览器**，不是自动存到手机。手机的 `127.0.0.1` 指手机自己，不能用它连接电脑。不要改 Python 绑定地址、开端口映射、反向代理或公网隧道来绕过这一限制。

## 手机怎么开始用

1. 在电脑生成一个**纯静态手机站点**：

   ```bash
   python3 -m health_journal.export_phone --output dist/phone-1.2.1
   ```

   输出目录必须不存在，防止覆盖。导出器只复制显式允许的网页资源并生成公开科室目录，不读取或复制个人 SQLite、附件、密码、Key、备份。

2. 将**仅此输出目录**部署到自己控制、可信、稳定的 HTTPS 静态站点。建议使用独立来源，不与不可信页面共享同一域名。不要部署整个工作目录、`.local-*` 或数据目录。
3. 在手机 Safari / Chrome 普通浏览模式打开网址，设置 12–256 字符的长密码。避免聊天内置浏览器和无痕模式。密码忘记后没有管理员重置或恢复服务。
4. 可从浏览器菜单添加到主屏幕；按钮名称及图标支持随系统变化。首次使用需联网；“备份互传”显示离线页面已缓存后，请实际断网试开一次。
5. 拍摄或导入一份**合成资料**，导出加密备份，再在另一测试档案试解密与合并。确认手机“文件”中真正出现备份，不能只凭页面提示判断成功。

本次没有替使用者创建 GitHub 仓库、开通托管、上传代码或部署公网网址。HTTPS、域名、托管账号和安全维护由部署者负责。`_headers` 可供支持该文件的托管服务使用；GitHub Pages 不会自动应用此文件，HTML 的 CSP meta 也不能替代 `frame-ancestors` 等响应头。公开源代码不代表健康档案应公开。

## 导入入口

- **拍一张**：请求系统后置相机选择器，拍后预览，再点“保存到手机”。不持续打开摄像头，不录音，不后台采集。`capture=environment` 是浏览器提示，部分设备仍显示文件选择器。
- **从相册选**：多选已有 JPG/PNG，查看清单后保存，每个文件分别显示成功、重复或失败。
- **选文件**：PDF、JPG/JPEG、PNG、UTF-8 TXT。单份最多 20 MB，每批最多 50 份，手机档案最多 500 份且原件合计 40 MB。
- **写几句**：记录日期、类别、可选科室与正文，保存成可携带的 UTF-8 文字原件；饮食/症状是个人自述，不自动成为诊断或已核实病历。
- **多页报告**：可连续拍摄或多选照片，各页独立保留；没有自动扫描、裁剪、合并 PDF、去反光、OCR、处方识别或医学影像分析。
- **HEIC/HEIF/Live Photo**：本版不支持，请在系统照片工具中导出 JPG 后导入，并保留原图。不能仅把扩展名改成 `.jpg`。不静默转码，不假称保留未经转换的原始照片。

文件字节保留；未去除照片 EXIF/GPS、患者姓名、报告编号或二维码。文件名中的不安全路径字符可能被替换，但不转换内容。签名与 SHA-256 检查不是病毒查杀、来源认证或医学核实。

1.2.1 拒绝无扩展名原件，互传名称不能含控制字符。电脑旧原件名如含制表符等，导出资料包时替换为下划线，仅改变包内名称，不改数据库或原件字节。旧版手机曾允许 `txt` 等无扩展名以及少数控制字符名称；认证解密旧 `.hjvault` 时兼容整理为 `原件.txt` 等可互传名称，并显示整理数量。原件内容、SHA-256 和加密协议不变，不放宽路径/类型/哈希检查。解锁本身不写回数据库，下次保存或导出时才携带整理后的名称；建议另存新版备份并保留旧副本。

手机资料夹可以搜索文件名和文字，按同一套 55 科关键词目录筛选。分类始终是待核对建议，只检查文件名/文字前 60000 字符，图片未识字，最多建议 12 科。手机尚未提供桌面的正式分科确认编辑。

## 两端怎样互传

### 手机 ↔ 手机：加密文件合并

1. A 手机“备份互传 → 导出加密备份 → 保存文件”，得到 `.hjvault`。
2. 用自己控制的方式将文件交给 B 手机。不要把密码与备份放在同一个公开位置。
3. B 手机先创建自己的档案，再选择“导入 / 合并加密备份”，输入 **A 的备份密码**。
4. 先查看新增/重复数量，再确认合并。B 的本地数据库继续用 **B 当前的密码** 加密，不会被 A 的密码替换。
5. 需要两边都保留所有内容时，将 B 的新备份再导入 A。

### 手机 ↔ 电脑：未加密的原件资料包

- 手机导出：备份互传 → 导出给电脑（未加密）→ 明确确认 → 保存文件。
- 电脑导入：原始资料 → 导入资料 → 导入手机资料包 → 校验并新增原件。
- 电脑导出：原始资料 → 导入资料 → 导出给手机（未加密）。
- 手机导入：备份互传 → 导入电脑资料包 → 核对新增/重复数量 → 确认合并。

格式为 `.hj-transfer.json`，**明文**包含原件文件名、类型、摘要和 Base64 字节；Base64 不是加密。请用受控的传递途径，导入后按个人保留策略处理副本。不要上传 GitHub、公共网盘、聊天群。手机 `.hjvault` 与桌面 `.zip` 不能互换；手机不是桌面 ZIP 的恢复工具。

**同步范围仅为原件**，包括手机创建的 TXT 随记。桌面的结构化诊疗记录、个人基本信息、餐单、AI 草稿、科室确认、修改历史、操作日志及 API Key **均不进入资料包**。因此不能用它替代完整桌面 ZIP 备份。

### 合并规则

- 相同 SHA-256 内容只保存一份；即使文件名不同，也保留接收设备已有的文件名，不覆盖原有分类。
- 同名但内容不同的文件都保留，不能用名称覆盖旧原件。
- 删除只作用于当前设备，不传播；导入旧备份可能重新带回已删除内容。不会用文件修改时间猜测“哪端更新”。
- 手机完整验证后用一个 IndexedDB 事务写入加密快照，版本令牌不匹配则拒绝覆盖；需锁定重新解锁，再重新导入。
- 电脑对资料包先全部校验，再在一个 SQLite 事务中新增。写入失败回滚本次数据库变更，并清理本次新附件；进程强制终止仍可能留下无引用附件，不能因此删除已有资料。
- 拍照/普通多文件导入逐份提交。某一份失败不会回滚已成功的其他文件；失败项显示原因并可重试。
- 未保存随记、未完成文件队列或待确认合并时，刷新/离开会请求浏览器显示警告。移动系统强制关闭页面不保证触发此事件，不能用警告代替保存与备份。
- 资料包最多 58 MB，加密文件最多 80 MB，解码原件合计最多 40 MB；低内存设备实际可用容量可能更低。

## 加密与保存的具体边界

- 浏览器 Web Crypto：PBKDF2-HMAC-SHA-256（600000 次、16 字节随机盐）派生 AES-256-GCM 密钥。每次保存使用随机 12 字节 IV、128 位认证标签；固定格式头作为附加认证数据。
- IndexedDB 仅保存格式头、加密数据与并发版本令牌。原件及文件名在加密载荷中；密码和不可导出的 CryptoKey 只保留在当前页面内存。
- 加密不隐藏是否使用应用、密文长度、浏览器来源、文件下载行为，也不防弱密码离线猜测。
- 5 分钟无操作后锁定；浏览器后台暂停计时器时会在重新可见时检查。处理中的保存先完成再锁定。尚未保存的文字/选中文件会被丢弃，需解锁后重写/重新选择；请及时保存。
- 解锁时网页、浏览器扩展、被攻陷的托管代码或设备可能访问明文。非提取式密钥不代表浏览器或系统不能使用密钥；不能保证内存、交换文件、截图、键盘词典或崩溃转储物理清零。
- 托管站点会收到加载静态资源所需的 IP、访问时间等网络元数据；原始实现没有将健康内容、密码或密文自动发送给托管方。**可信托管/更新来源仍是必要前提**。
- 不使用第三方脚本、字体、遥测。Service Worker 只缓存自身目录下的显式静态允许列表，不缓存 API、用户附件或密钥；没有后台同步和推送。
- 默认尽力存储可能被浏览器清理。`navigator.storage.persist()` 可以请求持久化，但是否批准由浏览器决定；批准也不防用户清理、设备丢失或损坏。主屏幕应用与浏览器是否共享资料依系统行为而异，不作保证。
- 同一来源中的脚本共享信任边界；不同项目路径不等于安全隔离。更换浏览器/用户配置/域名/端口可能看到另一份档案。
- 本版全快照加密，未实现增量附件加密、流式大文件、修改密码、恢复密钥、安全擦除或设备撤销。使用强密码，另存多个受控备份；忘记密码无法从本项目找回。

## 自动同步下一步如何做

推荐未来采用“各端本地数据库 + 端到端加密的同步中继”，而不是让手机裸连电脑 Python 服务。以下是**设计待办，不是当前已实现能力**：

1. 独立同步服务：可信 HTTPS、配对确认、短期设备令牌、撤销和重放保护；中继不能获得临床明文或解密密码。
2. 统一跨端数据模型：稳定记录 ID、版本/操作日志、每字段来源、附件内容寻址；桌面现有格式迁移必须可回滚。
3. 密钥管理：设备加入/丢失/撤销、恢复密钥、轮换和备份验证；不能把 API Key 作为同步密码。
4. 冲突处理：同条记录双端编辑必须提示并保留两版；删除使用带保留期的 tombstone，不能简单“最后写入获胜”。
5. 断网重试、幂等提交、分片附件、顺序独立合并、并发编辑、断电/重启/限额回归；不依赖不可靠的浏览器后台执行。
6. 手机云模型请求独立逐次授权、最小化发送和 Key 保护；不能将静态手机站点中的共享密钥公开给所有访客。
7. 外部安全评审和 iPhone/Android 真机验收通过后，才能称为自动多端同步版本。

不建议用同步盘实时同步运行中的 SQLite 文件，也不建议把含患者资料的 Git 仓库当同步数据库。

## 更新静态页面

每次改动静态资源要更换 `sw.js` 的缓存版本名称，整个导出目录一起发布。浏览器新 Service Worker 等待旧窗口全部关闭后接管，不强制重载正在填写的内容。使用相同可信来源保持本地档案可见；**不要用清理站点数据当升级步骤**。升级前先另存并实际核验加密备份。
